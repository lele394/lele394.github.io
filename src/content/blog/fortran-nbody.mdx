## Introduction

One of the most fundamental problems in computational astronomy and physics is the **N-Body Problem**: simulating the gravitational interactions between multiple bodies over time. From predicting planetary orbits to modeling galaxy dynamics, N-Body simulations are essential tools for understanding the universe. However, simulating even thousands of objects quickly becomes computationally intensive, making this an ideal testbed for exploring high-performance computing techniques.

This project presents a complete journey from a straightforward sequential implementation to a highly optimized multi-threaded CPU version and finally to GPU acceleration using modern parallel computing frameworks. Along the way, we'll explore the critical techniques needed to maintain accuracy, validate correctness, and squeeze every bit of performance out of modern heterogeneous hardware.

## Understanding the N-Body Problem

### The Physics

At the heart of any N-Body simulation lies Newton's law of universal gravitation. For each body $i$ in the system, we calculate the acceleration caused by all other bodies:

$$\mathbf{a}_i = G \sum_{j \neq i} \frac{m_j (\mathbf{r}_j - \mathbf{r}_i)}{\|\mathbf{r}_j - \mathbf{r}_i\|^3}$$

where:
- $\mathbf{a}_i$ is the acceleration of body $i$
- $G$ is the gravitational constant
- $m_j$ is the mass of body $j$
- $\mathbf{r}_i$ and $\mathbf{r}_j$ are the positions of bodies $i$ and $j$

The computational complexity here is crucial: for $N$ bodies, calculating all pairwise interactions requires $O(N^2)$ operations per timestep. With thousands of bodies and hundreds of integration steps, even a simple sequential implementation can take significant time.

### Numerical Integration: The Leapfrog Method

To accurately evolve the system forward in time, we use the **leapfrog integration method**, which provides excellent stability and accuracy for long-term simulations. The method consists of two steps:

**Position Update:**
$$\mathbf{r}_i(t + \Delta t) = \mathbf{r}_i(t) + \mathbf{v}_i(t) \Delta t + \frac{1}{2} \mathbf{a}_i(t) \Delta t^2$$

**Velocity Update:**
$$\mathbf{v}_i(t + \Delta t) = \mathbf{v}_i(t) + \frac{\mathbf{a}_i(t) + \mathbf{a}_i(t + \Delta t)}{2} \Delta t$$

This approach ensures numerical stability while maintaining the physical principles governing the system.

### Phase 2: Multi-Threaded CPU Acceleration with OpenMP

Once we validated the sequential implementation, the next logical step was parallelization. We chose OpenMP for CPU parallelization because it's:
- Widely supported across compilers
- Relatively easy to implement with compiler directives
- Flexible in optimization strategies
- Part of the Fortran standard

#### Parallelization Strategy

The key computational bottlenecks were:
1. **Acceleration calculation** - the $O(N^2)$ pairwise interactions
2. **Position and velocity updates** - $O(N)$ operations on all particles

We started by parallelizing individual loops, then optimized by merging them into a single large parallel region spanning the entire timestep iteration. This dramatically reduced thread synchronization overhead.

#### Variable Management

Proper scoping of variables was critical. In our final implementation, we used `default(none)` clauses to explicitly declare all variables as either private or shared, eliminating subtle bugs from unintended data sharing.

**Key private variables** for the acceleration computation:
- Loop indices
- Temporary distance and force vectors
- Energy caching variables

**Shared variables** mainly consisted of the position, velocity, and acceleration arrays.

#### Optimization Techniques

Beyond basic parallelization, we implemented several advanced optimizations:

**1. Pointer Swapping (No Data Copying)**
```fortran
subroutine swap_array(old, new)
    real(kind=8), allocatable, intent(inout) :: old(:,:), new(:,:)
    real(kind=8), allocatable :: temp(:,:)
    
    call move_alloc(from=old, to=temp)
    call move_alloc(from=new, to=old)
    call move_alloc(from=temp, to=new)
end subroutine swap_array
```

Rather than copying data when advancing to the next timestep, we swap pointers using Fortran's `move_alloc()`, eliminating expensive memory operations.

**2. Minimal Memory Footprint**
We reduced array usage to just four: positions, velocities, current accelerations, and next-step accelerations. This minimizes cache pressure and memory bandwidth consumption.

**3. Cache Optimization**
Position caching for the currently computed star and force vector caching further reduce memory access patterns, allowing the processor to work more efficiently with its cache hierarchy.

**4. I/O Optimization**
Using unformatted (binary) output instead of formatted text eliminates formatting overhead. Combined with asynchronous writes, we achieved a ~33% reduction in total execution time when using fewer threads than available cores.

#### Scheduling Analysis

OpenMP provides three scheduling strategies for distributing work:
- **Static**: Divide iterations evenly among threads (good for uniform workloads)
- **Guided**: Dynamically reduce chunk size over time (good for load balancing)
- **Dynamic**: Assign work on-demand (most flexible but higher overhead)

Our analysis showed that **dynamic scheduling** significantly outperformed static and guided approaches:

### Phase 3: GPU Acceleration with OpenACC

GPU acceleration represented the next frontier. We chose OpenACC for GPU porting because:
- It maintains similar syntax to OpenMP, easing the transition
- It abstracts away lower-level GPU programming details
- It's well-suited for computational kernels like N-Body

#### GPU Porting Challenges

The transition to GPU computing introduced a critical challenge: **race conditions**. In the original MT code, we exploited the symmetry of Newton's third law ($\mathbf{F}_{ij} = -\mathbf{F}_{ji}$) to reduce computation. However, this symmetry created data races when parallelizing across GPU threads.

**The Solution**: We eliminated the symmetry, computing all $N^2$ interactions explicitly. While this increases computation by a factor of ~2, it allows each GPU thread to maintain private force vectors—updating accelerations without atomic operations.

This trade-off is favorable for GPU architectures, where atomic operations cause significant performance penalties compared to CPUs.

## Lessons Learned

### What Worked Well

1. **Energy conservation** as a quick validation check—it immediately revealed bugs early in development
2. **Progressive optimization** from sequential → MT → GPU allowed proper validation at each stage
3. **Detailed performance profiling** (heatmaps, efficiency curves) identified optimal configurations
4. **Pointer swapping** and **memory optimization** delivered meaningful speedups without algorithmic changes
5. **Testing scheduling strategies** systematically revealed unexpected dynamic scheduling advantages

### Challenges and Trade-offs

1. **GPU race conditions** forced us to abandon symmetry optimization—a reminder that GPU programming requires different thinking
2. **Hyperthreading effects** limited scalability on the 48-core system beyond 23 threads
3. **Atomic operations** remain expensive even on modern GPUs, motivating the symmetry elimination strategy
4. **Diminishing returns** from asynchronous I/O when using many threads—parallel overhead becomes significant

## Conclusion

This project demonstrates the complete journey from understanding a classical computational physics problem, through careful sequential development and validation, to multi-threaded CPU optimization, and finally to GPU acceleration. The key takeaways:

1. **Never skip the sequential phase**—it's easier to parallelize correct code than to fix incorrect parallel code
2. **Validate at every stage**—energy conservation, deviation metrics, and qualitative checks catch bugs early
3. **Let data guide optimization**—heatmaps and performance metrics revealed optimal configurations far better than intuition
4. **Different architectures enable different strategies**—what's optimal for CPUs (symmetry exploitation) may be suboptimal for GPUs
5. **Modern hardware requires thought**—hyperthreading and cache hierarchies aren't free; they require careful consideration

The result is a simulation capable of modeling thousands of gravitational bodies with both accuracy and efficiency. Whether studying galaxy collisions, stellar dynamics, or planetary systems, this foundation can be extended to answer compelling questions about our universe.
